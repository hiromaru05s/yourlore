# LORE コスメティック制作規格 v1

2026-09-08。対象：カードスリーブ／シェルフ／デッキホルダー。

**この文書を今後の制作・発注の基準とする。** 今回決めた寸法・スロット・納品形式・表現制限を「必須」とする。性能値は制作予算として固定し、実機測定で不足する場合は全商品に共通する規格改訂で下げる。モデルや絵柄ごとの例外実装は作らない。

今回は画像生成と規格策定。以下の共通モデル、ローダー、購入・装備機能は実装仕様であり、既に実装済みという意味ではない。販売価格は別の経済設計で決める。

## 1. 商品の分け方

3カテゴリは独立した装備スロットとする。各スロットに無料デフォルトを必ず用意し、どの組み合わせでも正常に対戦できることを必須とする。

| カテゴリID | 買うもの | 共有する部分 | 装備の範囲 |
|---|---|---|---|
| `sleeve` | カード裏面の絵柄・質感・立体装飾 | カード本体、表面フレーム、紙の変形、当たり判定 | 自分の全カードに同じものを適用 |
| `shelf` | 使用済みカードを横向きに立てるケースの外観 | カード表示・格納スロット・枚数・シェルフからの戻り動作 | 自分側のシェルフ1台 |
| `deck_holder` | カードの束を上に置く低い台座の外観 | デッキのカード群・積層・ドロー出発点 | 自分側のデッキ下に1台 |

デッキホルダーは**台座**。箱、凹んだ受け皿、カードを囲う壁、上方へ出る縁を作らない。シェルフはカードを立てる**ケース**。役割を混同しない。

スリーブはカードID・タイプ・コストごとに選べない。デッキ内・相手手札・伏せカードの外観から内容が分からないようにする。全裏面に同じ商品IDと色バリアントを適用する。対戦開始時に3つの装備IDを確定し、その対戦中は変更しない。

## 2. 表現グレード：販売レアリティとは別管理

| 表現グレード | スリーブ | シェルフ／デッキホルダー | 新しい3Dモデル |
|---|---|---|---|
| `print` 絵柄版 | 共通カードに裏面画像を貼る | カテゴリ共通モデルにスキン画像を貼る | 不要 |
| `material` 素材・発光版 | 共通カードに色、粗さ、金属、発光マスクと共通シェーダー演出 | 同じ共通モデルで素材・発光演出 | 不要 |
| `sculpted` 立体版 | 共通カードの**裏面追加レイヤー**に彫刻・薄い立体装飾・任意の短いアニメーション | 規定の外形範囲と取付位置を守る専用モデル | 必要。ただしテーマ単位で再利用可 |

静止画を動かすだけなら必ずしも専用モデルは必要ない。2Dの発光マスク、UVの移動、色の脈動は `material` で扱う。立体の翼や開閉する機構が必要なときだけ `sculpted` とする。

同一形状の赤／青／黒版は、同じ `modelKey` とメッシュを参照し、テクスチャまたはパレットだけ変える。商品IDとアセットの参照先を分離し、色違いごとにGLBを複製しない。`print/material/sculpted` は技術的な区分であり、希少性や性能優位の表示には使わない。

すべての商品は**静止した軽量表示でもその商品の絵柄・配色・主要シルエットが残る**ように納品する。低画質設定で知らない無料商品に変わる設計にはしない。

## 3. 寸法と座標：全商品共通の基準

### 3.1 単位と基準カード

制作時の基準カードは **幅64mm × 高さ100mm × 紙厚0.32mm**。カード比率は現行コードの `0.64` を継承。実物の製造寸法ではなく、3D制作上の統一単位である。

- GLB書き出しは **メートル**。カードは `0.064 × 0.100 × 0.00032`。
- 文書内の `U` はカード幅。`1U = 64mm = 0.064m`。下記の表はU表記。
- glTFの右手系・+Y上を使う。プロップはXが左右、Yが高さ、+Zが自分側／手前。
- スケールは書き出し時に適用、rootは移動0・回転0・スケール1、負のスケールは禁止。
- 自分／相手側への向き変更はゲーム側のY軸回転で処理。鏡像化で文字や模様を反転しない。
- カードローカルはXY面、長辺がY、表面法線が+Z、裏面法線が−Z。文字の上は+Y。ゲーム内表示用の拡大はコンテナが担当。
- glTFの単位・座標・PBRは[公式仕様](https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html#coordinate-system-and-units)に従う。

### 3.2 共通の形状契約

| 対象 | 必須寸法／外形 | 原点・取り付け位置 |
|---|---|---|
| カード本体 | X ±0.5、Y ±0.78125、Z ±0.0025。角丸半径0.045U | 中央 `(0,0,0)` |
| スリーブ立体装飾 | XYはカードの角丸外形以内。Zは `−0.0325…−0.0025`、背面方向最大0.03U | `sleeve_back`、カード中央と一致 |
| デッキホルダー接触面 | **幅1.20 × 奥行1.85U**。小さい外角丸半径0.04U。全面Y=0 | `deck_mount=(0,0,0)`、天板中央 |
| デッキホルダー全体 | X ±0.65、Z ±0.975、Y `−0.14…0` | 天板を上限とし本体は下へ |
| シェルフ基部 | 幅2.00 × 奥行1.40U、Y `−0.12…0` | 基部上面中央 `(0,0,0)` |
| シェルフ全体 | X ±1.00、Z ±0.70、Y `−0.12…1.15` | `shelf_mount=(0,0,0)` |

盤面との接地は、台座の足裏Y=−0.14U、シェルフの足裏Y=−0.12Uに固定する。足裏以外をその高さまで埋める必要はない。ゲーム側はアンカーを盤面より各0.14U／0.12U上げ、台座の天板とシェルフの格納基準面を全商品で一致させる。カードの底辺は厚みと傾斜の貫通を避けるため0.001Uだけ浮かせる。

寸法比を商品ごとに自動フィットしてはいけない。大きな翼などを含めて収まるように縮めるとカードの見た目まで小さくなるため、カードと商品モデルのスケールを固定し、外形超過モデルを制作段階で直す。

### 3.3 デッキホルダーの空ける空間

- 天板接触域全体を同じ高さにする。接触面頂点のY偏差は最大0.0001U。
- **Y>0へ商品モデルが一切出ない**。角飾り、宝石、取手、開いた蓋、カードを囲う枠は不可。
- 幅1.10 × 奥行1.67U、天板上Y `0…0.80` をデッキの保護空間とする。粒子・アニメーションも入れない。
- 上のカードは商品GLBに含めない。ゲームが共有カードを生成する。束の表現枚数／見かけの高さは全ホルダーで同じ。
- 保護空間外の側面ではレリーフ、素材、底面の段差などを使える。天板の線模様はカラーテクスチャのみ。normal／height／displacementに入れない。
- `draw_exit` はゲームが算出する「いちばん上のカードの中央」。商品に固定したドロー開始点は持たせない。

### 3.4 シェルフの空ける空間とカードスロット

カードを**長辺が横になる向きで立てて**、手前から奥へ並べる。カードの長辺1.5625UがX方向、高さ1UがY方向。カードの出し入れは商品に依存させない。

- ケースが侵入してはいけない共通空間：X `−0.83…0.83`、Y `0…1.12`、Z `−0.61…0.59`。角飾りも侵入不可。底面との接触Y=0だけは許容。
- 左右のケース壁は `|X|≥0.85`。前壁はZ≥0.61かつY≤0.18。後壁はZ≤−0.63。外形全体は上記表に収める。
- `shelf_mount` は固定空ノード。個別商品にカードごとのスロットや格納枚数を持たせない。
- 表示スロットの最大数は12。少ないときも前側から埋め、13枚以上は奥の見かけの束とDOM枚数で表現する。論理枚数の上限を12にしてはいけない。
- 各カードの底辺を軸に奥へ8度傾ける。底辺中心は `(0,0.001,0.55−0.090j)`、`j=0…11`（j=0が手前の最新カード）。最奥カードの上端はZ約−0.579、X±0.78125、Y約0.991で保護空間内に収まる。
- publicに見せる表面は手前の最新カードだけ。奥側に隠れたカードの面は省略し、裏面や紙端だけで表現できる。
- この12枠の配置は共通ライブラリの責務。どの商品でもカードが埋まる・壁を突き抜ける・空に浮くことがないよう、基準カード入りの同一治具で確認する。

## 4. スリーブ仕様

### 4.1 画像版

- 編集原本：**2048×3200px、PNG、sRGB、全面不透明**。余白や背景付きの商品写真ではなく、カード裏面そのものを正面から描く。
- 通常配信：**1024×1600px WebP**、軽量：**512×800px WebP**。圧縮率より絵柄の品質を優先し、予算内で調整。
- UVは画像全域0…1。別の余白・外枠を焼き足さない。外形マスクと裏面の鏡像補正は共通カード側が担当。
- 重要な紋章は中央80%に収める。外周5%は色と模様を端まで延ばし、角のクリップや縮小に耐えさせる。
- カード名・効果文・数値・所有者名を裏面画像に入れない。
- 独自の透明穴、外形変更、タイプ別・カード別の裏面は不可。
- 既存 `sleeve_default.webp` は504×768で基準比率に完全一致しない。新規商品は上記比率を厳守し、既存品は初回移行で正規化する。

### 4.2 素材・発光版

画像版の必須ファイルに加えて、任意で `normal.png`、`orm.png`、`emissive.png`（最大1024×1600、補助マップは512×800／256×400へ縮小可。normal／ORMは線形扱い）。ORMはR=AO、G=roughness、B=metallic。色と発光色はsRGB。動きのない見た目を必ず `back.webp` に焼いた状態で持つ。全マップを最大解像度で同時使用しない。標準例は色1024×1600、normal 512×800、ORM／emissive各256×400。展開後メモリを§7の合算予算内にする。

v1で許可する演出プリセットは `none` / `emissive_pulse` / `foil_sweep` のみ。商品ごとのGLSLや任意JavaScriptは納品しない。周期4〜12秒、色はsRGBのRGB値、強さは0〜1の共通パラメータで指定する。強さ1の実際の輝度は基盤側で統一し、商品ごとに上書きしない。レイヤーの奥行きに見せる演出でも、カードの厚さや当たり判定を変えない。

### 4.3 立体版

- 共通カード本体・表面・紙端を置き換えない。背面に追加する装飾GLBのみ納品する。
- 背面のカード矩形を覆う薄い彫刻や、矩形内に収まる機構は可。カード外へ伸びる翼、カードごとに太さが違うケースは不可。
- 曲がる装飾は `bend_surface` グループ。全頂点を共通カードと同じ変形関数に通す。基準形はXY平面に沿った背面レイヤー。変形前頂点からX/Y位置と背面オフセットを取得できる構造とする。
- 背面中央にある小さな剛体飾りは `rigid_center` グループ、範囲X/Y±0.12U以内。共通カード中央の姿勢に追従させる。複数箇所を橋渡しする剛体パーツは不可。
- `bend_surface` の辺長は最大0.08Uになるよう分割。各点を変形する実装にする。単一の剛体GLBを曲がるカードに載せただけでは合格にならない。
- 商品が供給するスキニング／morphはv1では禁止。独自のrigやカードの曲げアニメーションを商品ごとに持たせず、固定UVや頂点の共通変形で扱う。動かす場合は装飾子ノードのTRSだけを使う。子ノードのローカルTRSを評価してから共通カード変形を適用する。全フレームで背面の安全範囲内に収める。
- 表向きのときは裏面装飾を非表示にする。相手の手札の全カードに高品質モデルを同時に付けない。小さい／重なった裏面は同商品静止版へ切り替える。
- ドロー／ドラッグ／裏返し／しなり／破砕中は**共通カード＋同商品静止画像**へ統一。開始・終了で装飾が飛び出したり別スリーブに変わらない。将来、変形対応の連続表示を実装してもこの静止経路は残す。

ここでいう立体版は「別形状のカード」を売ることではない。同じカードにリッチな背面装飾を付ける商品である。

## 5. シェルフ／デッキホルダーの制作方式

台座の方向性は[新しいデッキホルダー画像](../../3d-assets/2026-09-08-meshy/deck-holder-v3-pedestal.png)を参照。天板の金線は平面の色模様として扱い、形状には起こさない。画像から寸法を推測せず、§3を優先する。

`print/material` は共通マスターモデル（予定ID：`shelf_standard_v1` / `deck_pedestal_v1`）を再利用する。新しい絵柄を作るたびにMeshyへ投げ直す必要はない。`sculpted` だけ専用形状を納品する。

- 共通マスターのUVは一度確定したらv1内で変更しない。マスター自体は今回まだ未制作。**スキン量産前にマスターGLBとUVガイドを作成・承認する工程が必須。**
- 画像原本と配信用マップは同じUV。原本2048² PNG、標準配信1024²、軽量512²。色・ORM・normal・emissiveの最大4枚。
- カラーバリアント用の任意マスクは、既存テクスチャの未使用チャンネルを勝手に流用しない。使う場合は4枚予算内で独立マップとして宣言する。
- `sculpted` は独自UV可。ただし必須の静止プレビューと同一商品の軽量モデルを作る。
- 書き出し：GLB 2.0（モデル内のPNG/JPEG画像を含む）。任意外部URLや実行コードを含めない。制作原本は.blend等と未圧縮テクスチャを別保管。
- PBR metallic-roughness、`alphaMode=OPAQUE`を基本とする。窓や抜きが不可欠な場合だけMASK。v1は透過BLEND、屈折、透過ガラス、リアルタイム鏡、商品固有のライトを禁止。
- KTX2やDraco等は配信最適化の後工程。原納品には要求せず、対応デコーダを入れていない環境に圧縮だけ先行投入しない。[GLTFLoaderの対応と設定](https://threejs.org/docs/pages/GLTFLoader.html)を確認して導入する。
- マテリアル名：`body` / `trim` / `accent` の最大3種類。共通モデルの差し替え版はその既存スロットだけ使用。
- 3Dアセットにカード、枚数ラベル、影の板、カメラ、ライト、盤面、背景、パーティクルを焼き込まない。

### 正確な平面を得る作業順

1. 画像生成では立体形状用の参照を作る。天板は無地、模様は別の完成イメージへ。
2. Meshy等で形状を生成した後、制作ソフトでサイズ・軸・原点を正規化する。
3. 台座天板は生成メッシュから流用せず、寸法の決まった平面と側面接続へ作り直す。側面だけ生成形状を利用してもよい。
4. シェルフは指定の保護空間を貫通していないか確認し、内側を整形する。
5. 金の線や細かい模様は色テクスチャに描く。天板はフラット法線とし、normal/height/displacementは適用しない。面分割が多いだけでは凹凸は直らない。
6. 軽量モデル、UV、PBR、アンカー、プレビューを出力し、検査する。

**生成画像は完成モデルでもUVテクスチャでもない。生成GLBを未調整のまま販売用完成品にしない。**

## 6. アニメーション契約

ゲームのドロー・シャッフル・カード返却の軌道、入力可能タイミング、効果解決を商品が変更しない。商品アニメーションはそのイベントを受けて外観だけを動かす。

| イベント／クリップ名 | 用途 | 時間上限 | ループ |
|---|---|---|---|
| `idle` | 静かな発光／内部機構 | 1周期4〜12秒 | 可、継ぎ目なし |
| `focus` | ホバーまたは商品プレビュー | 0.25秒 | 不可 |
| `draw_react` | 台座からドローするときの反応 | 0.30秒 | 不可 |
| `receive_react` | シェルフにカードが戻る反応 | 0.40秒 | 不可 |
| `refill_react` | シェルフ→デッキのシャッフルに合わせる反応 | 0.80秒 | 不可 |

- クリップは任意。未納品なら静止を表示する。`print` はクリップなし、`material` は共通プリセット、`sculpted` のみGLBのTRSクリップ可。
- 動くのは `visual` 配下のみ。`deck_mount` / `shelf_mount` /ルート・共通カードをアニメーション対象にしてはいけない。
- 0秒の基準姿勢を納品し、cancel／早送り／画面破棄で即座に基準姿勢へ戻せること。
- 優先度は `refill > receive/draw > focus > idle`、同一商品でイベント演出をキューに積まない。後続イベントで置換し、入力の待ち時間を作らない。
- 全フレームで外形・保護空間を守る。開始／終了姿勢だけを検査して済ませない。
- `prefers-reduced-motion`／演出OFF／低画質では静止版。時計や盤面の注意表示と競合する点滅、常時粒子、画面全体の発光は禁止。
- v1は商品専用SE・外部VFXファイルなし。共通SEや共通演出を再利用する。将来追加は規格改訂とする。

## 7. 軽量化と画面上の制限

単位のMBは転送サイズ、MiBはGPUメモリの予算。これは**LORE内の設計上限**であり、glTFや端末一般の性能保証ではない。

| 商品1個の上限 | 標準表示LOD0 | 軽量LOD1 |
|---|---:|---:|
| スリーブ追加装飾 | 3,000三角形、2マテリアル／2 draw calls | 追加装飾なし、同商品画像 |
| シェルフ | 8,000三角形、3マテリアル／3 draw calls | 2,000三角形、1マテリアル／1 draw call |
| デッキホルダー | 4,000三角形、2マテリアル／2 draw calls | 1,000三角形、1マテリアル／1 draw call |
| スリーブ全配信データ | print 1MB、material 3MB、sculpted 5MB | 同商品画像0.3MB以内 |
| プロップ全配信データ | print/material 4MB、sculpted 8MB | 2MB以内 |
| プレビュー静止画 | 512² WebP、0.2MB以内 | 共用 |

- 三角形数とdraw call数はカード本体を除く追加コスメの値。マテリアルを共有していてもメッシュ分割でdraw callが増えるため、両方を検査する。
- 標準対戦中：リッチなスリーブは各プレイヤーのデッキ最上面1枚ずつ、**合計2枚**まで。詳細検査／ショップでは1枚だけ高品質表示可能。手札の裏面は静止画像。
- 1画面のコスメ追加予算：三角形40,000以下、draw calls16以下、ユニークテクスチャ64MiB以下、GLB＋画像初回転送24MB以下。6スロットの合計。カード本体・共通盤面等の性能予算とは別枠。
- 軽量表示：装飾モデルなし、両者のプロップはLOD1、追加三角形6,000以下・draw calls4以下・テクスチャ24MiB以下・転送8MB以下。
- バック画像を含め、同じモデル／テクスチャは参照共有。カードごとにTextureやGPU資源を複製しない。実際に使う2人分だけを試合前にロード。ショップ全商品を対戦中にロードしない。
- 静止フォールバック：プロップは背景透過512² WebP、カード・床・影の板なし。正投影カメラ位置 `(0,4,6)U`、注視点は原点、上方向+Y、縦横撮影範囲2.8U。自分向けはモデルY回転0°、相手向けは180°で2枚書き出す。原点は画像中心。画像を鏡像反転しない。表示側はこの撮影治具の投影と縮尺を再現し、カード群との位置を合わせる。試合中に残数を画像へ焼かない。
- 任意の組み合わせを保証するため、1商品で実際にロードするLOD＋画像には次の配分上限も適用する。全配信データとは異なり、非選択LOD・原本・ショップ画像は対戦中にロードしない。

| カテゴリ | 標準の展開後GPU／転送 | 軽量の展開後GPU／転送 |
|---|---:|---:|
| sleeve | 12MiB／4MB | 3MiB／0.3MB |
| shelf | 12MiB／4MB | 4MiB／1.5MB |
| deck_holder | 8MiB／3MB | 4MiB／1.5MB |

- 異なる商品6個でも標準64MiB／22MB、軽量22MiB／6.6MB以内になる。GPUは全テクスチャの展開後サイズとmipmapを含めて計算する。GLB内画像と外部画像を二重ロードしない。軽量プロップの補助マップは256²以下等へ下げて配分を守る。
- ファイル1個の上限に収まっていてもカテゴリ配分を超えれば出荷不可。制作予算は端末での実測を置き換えない。
- 読み込み失敗時は同商品静止画像、それも失敗ならカテゴリ無料デフォルト。失敗を理由に入力や試合開始を無期限に止めない。購入可否はサーバー所有権とする。
- 1280×720／1920×1080／390×844／844×390でカードとラベルの可読性・遮蔽・ドラッグを検査。リッチ版の基準はPCで60fps、軽量版は対象スマホで30fps以上を目標。**実機の基準機種は初回基盤実装時に固定し、未測定の商品を販売しない。**

## 8. データ規約・納品物

[機械可読の寸法・予算](constraints.json)、[商品アセットマニフェストのスキーマ](asset.schema.json)、[記入例](examples/)を併用する。マニフェストのスキーマ検証だけではGLB寸法・頂点・UV等は保証できず、別途アセット検査が必要。

```text
<category>/<asset_id>/v1/
  asset.json
  preview.webp                # 全グレード必須
  fallback-self.webp          # プロップ必須、自分向け透過画像
  fallback-opponent.webp      # プロップ必須、相手向け透過画像
  back.webp / back-low.webp    # スリーブ必須、1024x1600 / 512x800
  basecolor.png               # 任意：共通モデルのテクスチャ差し替え
  orm.png / normal.png / emissive.png
  model.glb / model-low.glb    # 専用プロップは両方必須、立体スリーブはmodelのみ
source/
  source.blend / textures/ / prompt.md / license.md
```

IDは `sleeve_biblion_ivory` のようにカテゴリを先頭へ。バージョンは破壊的変更時に増やし、既存バージョンを上書きしない。公開可能な `ready` マニフェストでは全ファイルにSHA-256とバイト数を記録する。記入例はファイル未制作の `draft` で、販売・ロード対象ではない。スリーブの静止フォールバックは `back-low.webp` を再利用する。`modelKey` は共有アセット登録簿のIDであり、未登録の値はロードしない。GLB内の必須root名は `cosmetic_root`、形状親は `visual`。

各モデルには、位置が固定されたカテゴリの空ノードを1個だけ含める。スリーブでは `sleeve_back`。LOD0とLOD1で取り付け位置が同じ。アセット内に価格・所有者・能力値を入れない。

プレビューには「装備なし／装備あり」「静止／演出あり」「標準／軽量」「デッキ0枚／1枚／40枚、シェルフ0枚／1枚／12枚／40枚」の検査画像を同梱する。購入者向けショップでは台座＋実際のカードを載せた状態も見せるが、納品GLBにはカードを入れない。

## 9. シャードの使い道・商品構造

この3カテゴリはすべてシャードで購入できる**外観商品**とする。枠の数、山札容量、ドロー速度、効果、当たり判定、見える情報は変えない。無料／有償シャードの扱いは既存の経済方針へ合わせ、独自の第三通貨を追加しない。

- 1商品＝恒久的な所有権。消耗品にはしない。各カテゴリ1枠に装備。
- 世界観の同じ3点は `collectionId` でまとめ、セット表示可能。各カテゴリは単品でも購入・装備できる。
- `productId`（何を所有するか）、`assetId/version`（何を描くか）、`offerId`（いくらで売るか）を別管理。
- 色違いを同梱にするか別商品にするかは商品設定。別商品でも内部モデルは共有。同梱色の場合は所有権1つで選択可能。
- 豪華版には同商品の軽量版を無償同梱。画像版と立体版を別商品にする場合は、既存所有者向けアップグレード商品を用意し、既に所有する内容を重複付与・二重請求しない。
- 通常版・素材版・立体版は価格差を付けられるが、**今回シャード価格は固定しない**。旧文書の1,000／2,000を新3カテゴリに自動流用しない。先に初期商品数とシャード供給量を合わせて決める。
- レベル、ランク、チャームとは別システム。これら3種にパワーを付けない。

### 購入と装備のサーバー契約（次の実装）

`catalog_product(product_id, category, asset_id, asset_version, collection_id)`、`catalog_offer(offer_id, product_id, shard_price, availability)`、`user_cosmetic(user_id, product_id, acquired_at)`、`user_loadout(user_id, sleeve_product_id, shelf_product_id, deck_holder_product_id)`、取引台帳を分離する。`user_cosmetic` は `(user_id,product_id)` 一意。

購入リクエストは `offerId + idempotencyKey` のみ。クライアントが価格や任意ファイルURLを指定できない。サーバーで販売状態・残高・所有を確認し、残高減算と所有付与と台帳を同一の原子的処理にする。再送・二重クリックでも消費と付与が1回だけであること。セット／アップグレードは全対象を1取引にまとめる。

装備時はカテゴリ一致と所有権を検証。試合開始時に `{sleeve, shelf, deckHolder}` の3商品IDとアセットバージョンを両者へ送る。相手に送るのは公開装備だけで、所持一覧やシャード残高は送らない。知らないIDでも対戦は続け、描画をデフォルトへ落とす。

## 10. 現状との差分と実装順

2026-09-08に実コードを確認：

- `client/src/shared/cards.ts`：`SLEEVES` はdefaultだけ、`sleeveUrl()` はIDを無視して同じ画像を返す。
- `server/src/social.ts`：default以外の装備を拒否、`/social/buy-sleeve` は410。DBに旧`sleeve/sleeves`列があっても販売・装備は機能していない。
- `client/src/screens/shop.ts`：コメントに販売中と残っているが、価格>0の商品がなく「販売中の商品なし」と表示する。
- `client/src/ui/paperCard.ts`：共通の変形するカードあり。`cardSurface.ts` は裏面を画像として取得するため、リッチ素材・装飾は現状の経路にまだない。
- `client/src/ui/pileModels.ts`：`makePile()` が同一の台座／シェルフ形状を生成。カード群とケースが同関数内にあり、描画層を分離する必要がある。
- `client/src/ui/duelScene.ts`：種類ごとのGLBローダーや商品アセット登録簿はまだない。
- 現在、静止した束の厚みは0.008U、動く紙の厚みは0.005Uで不一致。規格v1は0.005Uへ統一。束の見かけの積層間隔は別の共通表示パラメータとする。
- `docs/monetization.md` §8と `docs/world-bible.md` §8のシャード方針を継承する。

実装順は以下で固定：

1. 共通カード・シェルフ・台座マスター、UVガイド、寸法／保護空間の治具を作る。現在の紙厚とスリーブ比率を正規化。
2. 外観とゲーム状態を分離。アセット登録簿、ロード／解放、取り付けノード、LOD／静止フォールバックを作り、各カテゴリ1個の無料デフォルトを通す。
3. 画像版の全3カテゴリを1シリーズ分実装し、0枚／最大束／ドロー／シャッフル／リサイズを通す。
4. 所有・購入・装備・試合同期を実装。旧DB値は登録済みIDのみ移行し、未知値から任意資産をロードしない。
5. 素材版の共通演出を追加し、演出OFF／低画質で同商品として見えることを確認。
6. 立体版は各カテゴリ1個を先行制作。共通変形・アニメーション中断・上限と実機性能を検証してから量産する。

新商品に必要なのは「規格に合うアセット＋マニフェスト＋サーバー商品登録」。商品名ごとの分岐や個別CSS追加が必要になったら、量産開始前に共通側の不足を直す。

## 11. 出荷チェック

- [ ] 寸法、単位、軸、原点、アンカー、クリップ全フレームの外形が適合。
- [ ] 台座の上に壁がない。カード接触面は平面。シェルフの12枠保護空間へ侵入しない。
- [ ] 実カードの外形・フレーム・しなりを使って検査。商品画像だけの目視で合格にしない。
- [ ] 表裏、裏面方向、紙端、カード枚数、公開／非公開情報が正常。
- [ ] 標準・軽量・静止・GPU失敗のすべてでカード操作ができる。
- [ ] ドロー、返却、シャッフル、早送り、画面破棄、再接続で残像・無限待ち・リークなし。
- [ ] 3カテゴリを異なるシリーズで混ぜても当たり判定と可読性が変わらない。
- [ ] 個別予算と両者6スロット合計予算、対象実機のフレーム時間を満たす。
- [ ] スキーマ・SHA・ファイル実在・GLBバリデータ・ライセンス／生成来歴を確認。
- [ ] 二重購入／再送／残高不足／未所有装備／未知ID／対戦中変更のテストを通す。
- [ ] ショップで実ゲーム内サイズと軽量版もプレビュー可能。価格・含まれる色・内容が分かる。

寸法・見た目・販売のいずれかが未検証なら「制作途中」。スキーマが通ることやMeshyからGLBが出ることだけをもって販売可能としない。
