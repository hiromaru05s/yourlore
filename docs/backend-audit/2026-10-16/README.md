## 修正した問題

1. **P1: HTTPメソッドによる認証のレート制限・入力サイズ制限の回避。** `guardRequest` は POST/PUT/PATCH だけ検査する一方、認証ハンドラは DELETE 等でも処理した。ステージングの存在しないQAメール宛ログインで DELETE が405ではなく401になることを確認。リクエスト入口で認証ルートの許可メソッドを固定し、POSTの変更処理、GETの照会・認証リンク、OPTIONSのみを許可した。ログアウトもGETでは実行しない。
2. **P1（OAuth有効時）: 未認証の事前登録パスワードがGoogleログイン後も利用できる。** メールの所有者がGoogle認証すると `verified=1` だけが更新され、第三者が先に設定したパスワードでログイン可能になった。ローカルでGoogleのトークン応答を模擬して再現。未認証アカウントを統合する時だけ旧パスワード・セッション・メールトークンを一括失効し、認証済みアカウントの既存パスワードは保持する。`email_verified` も厳密にtrueを要求する。**現ステージングにはGoogle client secretがなく、このOAuth経路は無効。稼働環境で乗っ取りが発生したとの判断ではない。**
3. **P1: 未完成の対戦部屋を作成済みと扱う。** 勲章・デイリー課題のDB読込前に部屋をメモリへ公開していた。途中失敗後の再試行や同時承諾に409を返し、友達対戦側はそれを作成済み成功として扱う。さらに保存後のアラーム失敗で参加期限のない部屋が残り得た。部屋をローカル変数で完成させ、期限設定→保存→公開の順に変更。作成中は再試行可能な503、完了後のみ409にする。

`tests/backend-audit-oct16.mjs` の5ケースは修正前にすべて失敗し、修正後にすべて成功した。DB・アラーム障害はローカルで注入し、ステージングに意図的なサービス障害は起こしていない。

## その他の改善点（今回の修正範囲外）

- **P2: ステージングの認証設定。** 2026-10-16のsecret一覧は `AUTH_SECRET` のみ。Googleログインとメール送信は未設定で、登録はメール所有確認なしの既存フォールバックになる。パスワード再設定も実メールでの完了は検証できない。公開テストの本人確認要件を定め、Google/メール設定と認証フローを実環境で検証する必要がある。設定値を推測して追加していない。
- **P2: BOT部屋の作成上限。** `/api/rewards/bot/start` は認証を要求するが、アカウントごとの作成頻度・同時有効部屋数を制限していない。課題・勲章照会とDO作成の繰り返しによる負荷を抑える改善余地がある。負荷攻撃は実行していない。
- **P3: 期限切れデータの整理。** セッションは有効期限を検査して拒否するが、定期削除処理はない。監査時点の期限切れセッションは4件。終了済み部屋・課題・セッション等の保持期間を定めると、利用拡大時の蓄積を抑えられる。
- **P3: 戦績集計の拡張性。** `matches` に参加者・日時の複合インデックスがなく、プロフィール・勲章集計が履歴全体に依存する。現データ量で障害は確認していないが、実測に基づく索引追加・集計の保存が改善候補。

意図的な反復クーポン、テスト用マッチBOT、ガチャ配分は現在の仕様として扱い、変更しない。
